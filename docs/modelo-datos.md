# Modelo propuesto · no implementado

No es un esquema SQL ejecutable ni presume columnas/API de Boxmagic. Ajustar después de revisar exportación anonimizada, identificadores, estados, fechas y motor/versiones de hosting. Nombres siguientes son **internos propuestos**.

## Convenciones

InnoDB, `utf8mb4`; PK `BIGINT UNSIGNED` autoincremental. FK con mismo tipo y borrado `RESTRICT` salvo decisión explícita. `created_at`/`updated_at DATETIME(6)` UTC en todas las tablas, aplicación interpreta America/Santiago para fechas civiles. `?` indica nullable. Estados como `VARCHAR(32)` validados por aplicación y `CHECK` cuando lo soporte el motor. UUID externo se conserva como texto sin convertir a número. IDs externos con comparación binaria para no colapsar mayúsculas. No usar correo ni nombre como clave única.

## Identidad y ambigüedad

Separar cliente de membresías: una persona puede tener varias, incluso solapadas o futuras. Preferir IDs externos estables por fuente para ambos. Sin ID estable del cliente o membresía no asignar identidad por nombre ni email, aunque coincidan. Preparar candidatos para resolución manual y conservar un mapeo de identidad aprobado; la primera importación no puede inventar esa correspondencia. Mientras no exista clave estable o mapeo validado, rechazar/retener filas ambiguas sin cambios. Una huella del archivo evita repetirlo, pero no resuelve identidad entre exportaciones diferentes.

Renovación como nueva membresía y extensión de la misma son casos distintos; conservar historial. No borrar ausentes. Nunca importar datos médicos, biometría, contraseñas, documentos ni columnas fuera de una lista permitida. Registrar origen y fecha de actualización; si falta fecha del origen, marcar frescura desconocida.

## Fechas y vencimiento

Propuesta a confirmar: `ends_on` es el último día válido **inclusive** en America/Santiago; vence al inicio del día siguiente local. No asumir esta interpretación hasta validar Boxmagic. Si entrega instantes con hora/zona, usar campos UTC DATETIME(6) para instantes y conservar la zona de interpretación documentada; no truncarlos a DATE. Distinguir NULL de vencida. Usar calendario local con cambios de horario, no sumar 86.400 segundos para representar un día civil. Pendiente: suspensiones, fechas abiertas, anulaciones y qué significa «activo» en el archivo.

## Importación CSV futura

1. Solicitar muestra anonimizada, diccionario y alcance de exportación autorizada. No se conoce si Boxmagic ofrece CSV, API ni qué columnas exporta; confirmarlo antes de implementar. Preferir CSV si está disponible.
2. Admin autenticado sube a directorio privado con nombre aleatorio, tamaño/filas/campos limitados y caducidad. Validar extensión, contenido y codificación; BOM, delimitador y fechas se eligen/validan explícitamente. No confiar solo en MIME. No ejecutar fórmulas CSV; neutralizarlas si se reexportan incidencias.
3. Calcular SHA-256; detectar lote existente para devolver resultado sin duplicar. Un lote fallido puede reintentarse bajo el mismo ID con historial de intento, nunca saltarse silenciosamente por existir. Cambio de mapeo requiere revisión; idempotencia de entidades es independiente de huella del archivo.
4. Vista previa con mapeo de columnas aprobado, errores por fila y cobertura/frescura. No copiar nombres de columnas supuestos. Validar IDs duplicados/conflictivos, fechas, FK, longitudes, emails y valores. Rechazar filas ambiguas y mostrar conteos; ninguna mutación de clientes durante vista previa.
5. Confirmación con CSRF asociada al hash del archivo, versión de mapeo y vista previa. Transacción InnoDB: reservar lote con UNIQUE y bloquear concurrencia, aplicar únicamente filas válidas confirmadas mediante consultas PDO preparadas; upsert por identidad aprobada, comparación con estado actual e historial por evento. No sobrescribir dato más nuevo con exportación anterior; si falta fecha, revisión explícita. Registrar creadas/actualizadas/omitidas/rechazadas; commit conjunto. Error técnico: rollback completo y estado failed registrado en operación separada. Error de fila validado: omitir esa fila y conservar incidencia, sin medias membresías.
6. Exportaciones mayores al límite del hosting requieren lotes de trabajo con checkpoints y transacciones acotadas, a diseñar tras medir. No suponer procesos persistentes. Limpiar archivo temporal tras plazo acordado; conservar huella y conteos, sin CSV real en Git o área pública.

No interpretar falta en exportación activa como baja, ni parcial como inventario completo. La elegibilidad de avisos exige una fuente reciente con cobertura que permita comprobar renovaciones. Restauración y retención de base/archivos deben probarse antes de importar datos reales.
